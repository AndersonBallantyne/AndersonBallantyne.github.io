When "Anonymized" Isn't: A Mid-Build Data-Exposure Pivot

A 30-row CI fixture had already passed one anonymization pass — a masked ID, a masked email domain — and was already sitting in a public repo. It still wasn't clean. This is the story of finding that out mid-build, the mistake I made while fixing it, and the two different git-history purge techniques I used on purpose, not interchangeably.

SQL_TEST_01 · Build 5~9 min read

Build 5 of this project was supposed to be the boring one: wire up a public GitHub repo, add a CI workflow, prove the schema and pipeline build from a genuinely empty environment on every push. Infrastructure work. The kind of build where the interesting part is a green checkmark.

It didn't stay boring, because about two-thirds of the way through, I asked myself a question I should have asked at the start: should I just mask the whole file, or is the small fixture I already built good enough?

The fixture that looked fine

The real dataset behind this agent is a genuine equipment-allocation export — 1,535 rows, never committed to the repo, living only on my machine. CI needs something to run against, though, so Phase 1 of Build 5 built a small fixture: 30 real rows, with the allocation ID replaced by fake sequential numbers and the email domain swapped to a fixture-only domain. That felt like anonymization. It passed a glance-test. It got committed and pushed to a public remote.

Here's what I hadn't actually checked: everything else in those 30 rows was untouched. Real department codes. Real dates and durations. Real equipment descriptions — brand and model, specific enough to identify actual inventory — with only the embedded internal asset-tag numbers scrubbed out.

The gap wasn't "does this reveal who the institution is." It didn't — the domain was already masked back in an earlier build. The gap was that I'd quietly narrowed "anonymized" down to "not attributable," when the actual bar is broader: no real operational or proprietary data goes public, attributable or not. A masked ID number doesn't anonymize a real department code sitting three columns over.

Under the real standard, the fixture that had already passed review — and was already public — failed it.

What actually needed to be true

Once the bar was named correctly, the fix couldn't be "mask two more fields in the fixture." Every field needed a deliberate decision: keep it real because it's not proprietary, or replace it because it is. I ended up scrapping the real/fixture split entirely and building one official synthesized dataset instead — data/ALLOCATION-synthesized.csv, matching the real export row-for-row, used identically by local dev, CI, and the eval harness. No separate fixture to ever drift out of sync again.

FieldTreatment
renewal count, all three dates, duration, resource countkept real, unchanged — nothing proprietary in these alone, and keeping them real means row counts and aggregates still match ground truth
allocation IDrandom unique 7-digit IDs, sampled (not sequential) — categorically different shape from the real 6-digit IDs
department codea 1:1 fictional remap, exact distribution and plurality shape preserved; the real→fake key itself never goes in the public repo
email domaininstitution-specific domain family swapped to a fixture domain; a generic public provider (already present in a handful of real rows) left untouched — it isn't the institution's own domain, so it isn't identifying
equipment descriptionfully synthesized from a ~50-item pool spanning the same real categories, different specific brand/model combinations

The department-code mapping is the one piece that can never be public — it's the literal real-to-fake key, and publishing it next to the fake values would let anyone reverse the mask. It lives in two git-ignored, local-only files instead: a human-readable reference and the actual Python module the synthesis script imports at runtime. Same treatment this project already gives its local credentials file.

The mistake I made fixing it

This is the part worth being honest about. The first version of the synthesis script hardcoded that department mapping directly as a dictionary in the committed file — the exact mapping that was supposed to stay private, sitting in plain sight in the script meant to protect it. I'd built the "don't leak this" fix by leaking it.

Caught before it ever left the machine. This project has a standing habit: before anything sensitive gets purged from git history, verify the purge worked with a direct pickaxe search across full history — git log --all -S"<string>" — rather than trusting a tool's own success message. Running that same check on the new script, before pushing, surfaced the hardcoded mapping immediately.

Because the commit hadn't been shared anywhere yet, the fix didn't need a history rewrite — a plain git commit --amend was safe. I went one step further and pruned the flawed blob out of the local repo entirely:

git commit --amend
git reflog expire --expire=now --all
git gc --prune=now

The lesson generalizes past this one script: a script that exists to protect a secret is itself a place a secret can leak, and it gets exactly the same scrutiny as the data it's protecting — not less, because it's "just tooling."

Two purge techniques, used on purpose

By the end of this build, three separate pieces of git history needed rewriting: an earlier, unrelated leak of old (already-rotated) dev credentials; the now-superseded 30-row fixture; and one hypothetical example question in an old build's documentation that happened to quote a real department code. I used two different git filter-repo techniques, deliberately, not interchangeably:

  • --path ... --invert-paths — whole-file removal, used for the fixture CSV. It wasn't being edited, it was being replaced wholesale by the new synthesized dataset, so the entire file's history could go.
  • --replace-text — an in-place string scrub, used for the credential leak and the one leaked department code in an old doc. Both cases needed the file's history to survive; only a specific string inside it needed to disappear.
The choice between them wasn't automatic. Before scrubbing that department code with --replace-text, I checked whether the string was safe to blanket-replace across the whole history — some of this project's department codes are short enough to be substrings of ordinary English or code words that appear constantly in a codebase (one of them, for instance, is a substring of both "transform" and "transaction," words used throughout this project's own source). A blind replace on a colliding string would have silently corrupted unrelated text everywhere it appeared. The one actually being purged didn't collide with anything — confirmed by a full-history search first, not assumed.

The two shapes, and the check that ran before and after every one of them:

# whole-file removal - the file is being replaced, not edited
git filter-repo --path data/allocations-fixture.csv --invert-paths

# in-place string scrub - the file's history needs to survive,
# only one string inside it doesn't
git filter-repo --replace-text replacements.txt

# the actual check, run before trusting either one - not the tool's
# own success message, a direct search across full history
git log --all -S"<the string being purged>"
View diagram · which purge technique, and why

Two of the three rewrites also required a force-push, since real commits had already reached the public remote and history had diverged. Both were confirmed explicitly before running, and each rewrite was preceded by a full local backup bundle, kept outside the repository entirely — the exact place you don't want to discover a backup is missing.

The part that surprised me

Rebuilding the dataset properly turned out to fix something unrelated for free. A separate eval suite had three test cases that had never fully worked in CI. Two of them turned out to depend on values the new synthetic dataset preserved exactly — a department plurality count and a renewal-count total, both untouched by the rebuild — so they just started passing. The third genuinely couldn't work in CI, but for a different reason than I'd originally assumed: it expected a scratch table saved by an earlier eval case to still exist, but that case's own cleanup step correctly dropped the table right after using it. A local "pass" I'd seen earlier turned out to be a false positive — a leftover table from unrelated manual testing months earlier happened to satisfy the check by coincidence. Once I understood the real cause, the fix was a small, honest one: skip that specific case in CI with an explicit flag, rather than let it fail unpredictably or pass on a coincidence nobody could see.

What I'd tell someone doing this for the first time

  1. Name the actual bar before you build against it. "Anonymized" quietly narrowed to "not attributable to the institution" without anyone deciding that on purpose. The real requirement — no real operational data public, period — was broader, and the fixture had already failed it while looking fine.
  2. The tool that protects a secret gets the same scrutiny as the secret. The leak wasn't in the data this time; it was in the script written to mask the data.
  3. Verify a purge by searching, not by trusting the tool's exit code. A direct pickaxe search across full history is what actually caught both leaks in this build — the original credentials and the hardcoded mapping.
  4. Not every history rewrite is the same operation. Removing a superseded file and scrubbing one string out of a file that needs to survive are different techniques with different risk profiles — check for string collisions before a blanket replace, don't assume.
  5. A document describing a leak can itself leak the same thing. The most tempting place to accidentally reproduce a purged secret is the write-up explaining how you purged it — this post included. Anything narrating a redaction gets swept for the same strings it's narrating, on purpose, every time.
