Two Prompt Fixes That Didn't Work, and Why "Remember to Write This Prefix" Never Holds

The day the live public demo launched, the first real question exposed a gap in a fix that had already shipped and passed every existing test. Two prose-wording rewrites were tried and reproduction-tested first, back to back - neither changed the outcome. The fix that actually worked replaced a text convention with a categorical tool argument.

SQL_TEST_01 · Build 7 follow-up~6 min read

The 2026-08-10 fix (see the previous post) taught the verifier to tell two situations apart: a claim that actively contradicts the tool evidence, and a claim the evidence simply doesn't confirm or deny. The second case was meant to get a softened reason, prefixed "Verify further:", instead of a flat unsupported verdict. It passed all five regression cases at the time. It had never actually been exercised live by a case built for exactly that gap - until the day the public demo went live and someone asked it the most natural question there is.

The question that found it

"Tell me about this project?" The agent answered correctly on the technical facts it had just retrieved via search_docs and a follow-up SQL query, and then also described the underlying data as "equipment allocations - checkouts and returns by patrons/departments." That description is true. It is not, however, something either of that turn's two tool calls actually returned - it came from the model's own general awareness of what this project is, the same way it would answer if asked to summarize any system it has genuine background knowledge of.

The verifier caught the gap correctly: the schema claim wasn't in that question's evidence. What it got wrong was the framing - it returned a flat, hard unsupported, with no "Verify further:" softening, even though nothing in the answer actually conflicted with the evidence shown.

Reproducing it, not assuming it

Before touching anything, the exact scenario was rebuilt outside the app: same question, same two tool calls re-run for real, same proposed answer, fed straight into verify_answer() three times in a row.

Result: supported: False on all three runs, and the prefix never appeared once - even though the verifier's own reason text kept independently describing the exact situation the prefix exists for: "the evidence does not explicitly state," "cannot be verified from the evidence provided," "goes beyond what the evidence actually shows." None of the three reasons described an actual contradiction. The classification mechanism, not the model's judgment, was the problem.

Two fixes that didn't work

The prompt had two paragraphs: one telling the model when to hard-fail an answer, one telling it when to soften to "Verify further:" instead. Reading them again, both paragraphs turned out to describe the same evidentiary situation in different words - "claims something the evidence never shows" (hard-fail paragraph) and "isn't present in it at all" (soft paragraph) are the same fact, phrased twice, pointing at two different outcomes.

AttemptChangeResult on the same 3x reproduction
1Removed the overlapping phrase from the hard-fail paragraph, consolidated it into the soft paragraphNo change - 3/3 still hard-failed, still no prefix
2Clarified that confident phrasing isn't itself evidence, broadened the soft paragraph's explanation beyond "an earlier conversation turn"No change - 3/3 still hard-failed, still no prefix

Six runs, two rewrites, zero change in outcome. That consistency was itself the useful signal.

Two wording rewrites producing an identical result each time is not evidence that the wording is almost right - it is evidence that wording was never the actual lever. Asking a fast model to remember a text-formatting convention ("start your answer with this exact phrase") buried inside a longer set of rules is not something structured tool-calling reliably holds onto, regardless of how the surrounding rule is worded.

The fix that worked

The boolean supported field, plus a prose instruction to prefix reason under specific conditions, was replaced with a three-value enum the model has to choose as a real tool argument: "supported", "contradicted", or "unconfirmed". The Python code - not the model's prose habits - now derives the caller-facing (supported, reason) tuple and attaches the "Verify further:" framing when the verdict is "unconfirmed".

# verify_answer.py - before: a boolean plus a prose convention
"supported": { "type": "boolean" }
# prompt: "...start reason with 'Verify further:' for that case"
# -> the model has to remember a text-formatting habit under load

# after: a categorical tool argument the model must choose
"verdict": {
  "type": "string",
  "enum": ["supported", "contradicted", "unconfirmed"]
}
# the framing is now attached in code, once the model has committed
# to a category - not left to the model to remember to write
View diagram · where the reliability moved
Re-verified: the same live scenario re-run post-fix now stays internally consistent every time - reasoning and verdict agree, and one run even genuinely flipped to supported=True on real judgment variance rather than a stuck default. All 5 verify_eval_cases.py cases still pass, and 3 new unit tests cover the contradicted/unconfirmed/unexpected-verdict paths directly.

The throughline

A rule a model has to remember to format correctly is weaker than a rule it has to choose from a fixed list. Reasoning and formatting are different tasks, and stacking them onto one free-text field lets the first succeed while the second silently fails - the model's own explanation kept proving it understood the distinction, while its output kept losing it.

  1. Reproduce before rewriting. Two prompt-only fixes were tried and disproven by direct reproduction before reaching for a structural change - neither wasted more than one test cycle.
  2. A flat outcome across rewrites is itself a finding. Six identical results across two different wordings ruled out "the wording is almost right" and pointed at the mechanism instead.
  3. Push classification into the schema, not the prose. Structured tool-calling is reliable at forcing a categorical choice; it is not reliable at enforcing a remembered text convention layered on top of one.
  4. Keep the external contract stable while fixing the internals. Every caller of verify_answer() still receives the same (supported, reason) shape it always did - the fix moved where the distinction gets made, not what any other file needs to know about it.

Full detail - the exact reproduction runs, both rejected wordings, and the final prompt/schema - is documented in the project's living command reference, under src/verify_answer.py.
