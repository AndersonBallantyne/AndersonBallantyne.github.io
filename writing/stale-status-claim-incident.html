A Wrong "Still Unresolved," and a Verifier That Learned to Say "Verify Further"

A truncated chunk made an already-fixed incident look open again. The quick fix for that was correct and still blew one question's cost to 202,821 tokens before it ever shipped — caught by re-testing, not by luck. The real fix turned out to be a data-pipeline gap, not a smarter prompt. Later the same day, a completely different verifier gap surfaced: a genuinely correct answer flagged as unsupported, not because it was wrong, but because the check meant to confirm it structurally couldn't see the evidence that made it right.

SQL_TEST_01 · Builds 7 follow-ups~7 min read

This project's agent answers questions about an equipment-checkout database and its own build history by writing SQL and searching its own documentation. A second agent — the verifier — checks every answer against the tool evidence gathered for it before showing a green or red badge. Both had been running in production for days. A routine verification pass — re-asking questions that should already be settled, just to confirm they still were — is what started this.

Finding 1 · a fixed incident, reported as still broken

Two live answers, asked days apart, both confidently called an already-resolved deployment gap from an earlier incident "still unresolved." It wasn't. The real root cause: this project caps every tool-result field at 500 characters before it reaches the model, and the source documentation chunk describing that incident's resolution got cut off right before the word "Fixed." The model was reading a truncated sentence and reporting exactly what it said — a genuinely grounded answer, built from data that had been silently cut off mid-sentence.

The quick fix, and what it cost: a caution rule — don't conclude a negative status from a chunk that looks truncated, verify further if unsure — restored correctness. Tested against the two known-bad questions, it worked. Tested more broadly, it reintroduced an anti-pattern from a separate incident days earlier: a soft, open-ended "keep searching if unsure" instruction with no bounded action caused the model to chase the truncated evidence through repeated re-queries. One question's cost went from 41,417 to 202,821 tokens — worse than doing nothing.

Caught by re-testing before calling it done, not after shipping it.

The fix that actually held moved the caution rule from an instruction ("verify further") to data: a consolidated, always-current "Known Open & Deferred Items" table, so a status question never has to re-derive an answer by searching in the first place. But that only fixed the two questions that had actually been tested. A closer look at the underlying data found the real shape of the problem: 127 of roughly 532 documentation chunks already exceeded the 500-character cap — some by over 6,000 characters — because the extraction pipeline that built them had never enforced a size limit at all. The truncated incident chunk wasn't a one-off; it was one instance of a pipeline gap that could resurface anywhere, on any question, at any time.

The real fix: chunk-splitting moved to extraction time — any chunk over 450 characters now gets broken up on sentence (falling back to word) boundaries before it's ever stored, so nothing downstream can be long enough for the 500-character cap to cut off mid-fact. Re-ran the real extraction: 532 chunks became 769, and zero exceed the cap, dataset-wide. Final re-test on both original questions: correct, at 15,491 and 18,992 tokens — cheaper than the very first attempt, not just cheaper than the regression.

The actual truncation, and the boundary that used to sit past it:

# tools.py - the cap that was always there
MAX_FIELD_CHARS = 500  # applied to every tool-result field

# the source chunk, before this fix (real text, cut mid-sentence)
"...the deployment-verification gap from 2026-08-07 was
 traced to a stale Streamlit process and"[truncated, 743 total chars]
# the word "Fixed" was 40 characters past the cut

# extract_doc_chunks.py - the fix, applied once at extraction time
CHUNK_SPLIT_TARGET_CHARS = 450
chunks = [piece for chunk in chunks for piece in _split_long_text(chunk)]
# splits on sentence boundaries, falls back to word boundaries -
# no chunk this pipeline produces can reach MAX_FIELD_CHARS again

Finding 2 · a genuinely correct answer, flagged as unsupported

Sample browser testing of a new feature turned up a case that looked, at first glance, like a bad answer: a follow-up question listed eleven columns for a database table, but the verifier's own evidence for that specific question showed only a row count — no column query at all. Red badge, plausible-looking bug.

It wasn't a bug in the answer. Checking the actual log: the same table's columns had been queried for real, correctly, about 50 seconds earlier in the same conversation — still sitting in the tiered conversation memory the model actually had open when it answered. The model reused a real fact it had genuinely retrieved. The verifier's own evidence, though, is scoped strictly to that one question's fresh tool calls — it has no visibility into anything gathered in an earlier round, even a round the model's own context window still held.

Option consideredWhy it wasn't the fix
Expand the verifier's evidence to the last few roundsReal cost growth on every check, and risks verifying against evidence the model's own context window may not have actually included — a different kind of ungrounded check.
Flatten the entire conversation into the verifier's evidenceUnbounded growth as a session gets longer — the exact anti-pattern behind a 176,252-token conversation-memory bug from a separate incident, reintroduced in a new place.
Teach the verifier to phrase uncertainty honestlyCheap, bounded, no schema or logging changes — the one actually shipped.

The fix that shipped taught the verifier something narrower and more honest: from a single question's evidence alone, it genuinely can't tell a claim that was fabricated apart from one that was correctly carried over from a moment earlier in the conversation — both simply look like "not in what I can see." What it can tell apart is whether a claim actively contradicts the evidence in front of it, versus one the evidence merely doesn't confirm or deny. A direct contradiction keeps the sharp, unqualified "unsupported." A claim that isn't in the evidence but doesn't conflict with it either now gets the verdict's reason prefixed "Verify further:", naming exactly what can't be confirmed — honest about the limits of a single-shot check, instead of implying the claim is simply wrong.

# verify_answer.py - VERIFIER_SYSTEM_PROMPT, the actual addition
"""
Not every unbacked claim is a contradiction, though. This evidence
set only covers tool calls made for this specific question - it has
no visibility into earlier turns of the same conversation. [...]
For that specific case, still set supported=false, but start reason
with "Verify further:" and name exactly which claim(s) can't be
confirmed from this evidence, rather than declaring them wrong
outright.
"""
# supported stays a plain boolean either way - only reason changes,
# so no schema, logging, or UI code needed to change
Re-verified on the exact real case: the badge still reads unsupported (this check still can't confirm the claim from what it was given), but the reason now says "Verify further: … which has no visibility into any earlier schema queries that may have been run" — not a claim that the answer is wrong. All five existing regression cases, including a hard-contradiction case built specifically to stay unqualified, still pass with the new wording.
Correction: this specific fix didn't hold. Passing every regression case turned out not to mean the wording actually fired on a real, unrehearsed question — the first one the public demo ever got asked exposed it: the model's own reasoning kept describing exactly the "not confirmed, not contradicted" case above, and the verdict still came back a flat, unqualified unsupported anyway, with no "Verify further:" softening. A boolean plus a "remember to write this prefix" prose instruction turned out not to be something structured tool-calling reliably holds onto. The actual fix, and the full reproduction that found this, is in the follow-up post.

Same day, in brief

Three smaller pieces closed out the same day, each triggered directly by one of the findings above rather than planned in advance:

  • Scratch-workspace cleanup. The agent's writable scratch tables had no lifecycle policy at all. Built collaboratively over several rounds of design questions rather than decided solo: two-tier staleness (worth mentioning at 7 days, actually offered for deletion at 30), deletion reachable only through a real UI button click — never an agent tool call, so it never depends on a chat reply counting as consent — and a follow-up gap (what if someone wants a table gone immediately, not after 30 days?) closed the same day it was raised, with the age gate still fully enforced for every other path.
  • Isolating which tool call causes a token spike. The Anthropic API only reports token usage per API turn, never per tool call, and a single turn can make more than one call at once — confirmed live, a two-call turn shares one usage number. Result size (characters) turned out to be the right proxy instead: exactly attributable to the one call that produced it, no cross-turn ambiguity, the same technique this project already uses elsewhere to keep individual fields from ballooning a question's cost.
  • A documentation rewrite that found two more pipeline bugs. Swapping a rewritten project-overview page into the documentation search index surfaced a second real extraction gap: bullet lists and a structured build summary weren't recognized by any existing extraction rule, so the swap silently indexed 3 of the page's 21 real chunks. Fixed with a new extraction rule for that content shape. Separately, removing the old page from the index left its rows behind with no cleanup path — the same "orphaned rows" shape a much earlier repo audit had already found once, in a different corner of the project.

The throughline

Two different failure classes, the same underlying move both times: when a check can only see part of the picture, the honest fix is to say so precisely, not to guess harder or search more. A truncated chunk isn't proof of a negative status — it's proof of nothing, and the fix was admitting that as data, not chasing the missing tail with more queries. A verifier with no visibility into an earlier round isn't proof an answer is wrong — it's proof of a blind spot, and the fix was naming that blind spot in the verdict's own language instead of expanding the check's reach at real cost.

  1. A caution rule with no bounded action is a liability, not a safeguard. "Verify further" told the model to keep searching, with no limit — the same anti-pattern this project had already named and moved away from once, three days earlier, in an unrelated fix.
  2. Fix the mechanism, not the instance. A prompt rule for two known-bad questions is a patch. Finding that 127 other chunks shared the same silent risk, and closing the pipeline gap that let any of them exist, is the actual fix.
  3. "Unsupported" and "genuinely wrong" aren't the same claim. A check with incomplete evidence should say what it can't confirm, not imply the thing it can't confirm is false.
  4. Cheap, bounded, and honest beats broad and expensive. Every alternative considered for the verifier gap would have made every future check more costly to fix one specific case. A wording change fixed the actual problem — miscommunicating certainty — for free.

Full timestamped accounts — every question, every fix, every token count, in order — are in the project repo: the 2026-08-10 incident audit covers Finding 1 in full, and the living command reference documents the verifier change and everything in "same day, in brief."
